Where a read request spends its time

Follow one read from the browser to the database and back, and see why the slowest hop, not the average one, sets how fast it feels.

7 Oct 2026 · 9 min · 4 figures

A page that loads in 80 milliseconds feels instant; one that loads in 800 feels broken. Between the two there is rarely one slow component. There are five or six hops, each fast on average, and a tail that compounds.The thresholds are old but hold up: about 100 ms reads as instant, about one second keeps a train of thought, ten seconds loses it.

This post walks one read through a small, ordinary system: a browser, a load balancer, a pool of api servers, a cache, and a database with a replica. Then it looks at two effects that make the average a poor guide: fan-out, and queues near capacity.

The path of one read

The system lives in one region. Scroll on and the drawing follows the text; use explore to look around it yourself.

Seen from above, a read is four hops: the browser to the load balancer, to one of three api servers, to postgres, and back the same way. Each arrow is a network round trip, and each box adds its own work.

The first hop is the most expensive one we do not control. A new connection pays for a TCP handshake and a TLS handshake before the first byte of the request; a resumed one skips most of that. The load balancer terminates TLS, so this cost ends here.

The api server asks redis first. A hit costs a few hundred microseconds inside the region and the database never hears about it. With a hit rate of 95%, the cache decides how most requests feel.

A miss goes to postgres. An indexed read of one row is a few milliseconds, most of it waiting on the network and the buffer cache, not on the disk. This is the hop that sets the tail.

When postgres stalls, a vacuum or a lock, the api server waits until its timeout. The request does not fail fast; it fails late, holding a connection the whole time, and the requests behind it queue.

Work that the reader does not need to wait for leaves the request entirely. The api puts a message on the orders queue and answers; the email worker picks it up later. The dashed lines are messages nobody waits on.

Why the tail is the common case

A page is rarely one request. A dashboard that renders ten widgets, or a search that asks a hundred shards, waits for the slowest answer. If each server is slow one time in a hundred, the chance that at least one of N is slow is 1 − 0.99N.

The usual fixes all cut the dependence on the slowest server: hedge a request to a second replica after the p95, cap how long a fan-out waits, or return partial results.

Hedging adds load. At a p95 trigger it sends about 5% more requests; on a system already near capacity that 5% moves it up the curve in the next section.

Queues and the knee

Every hop above has a queue in front of it: a connection pool, a thread pool, a socket buffer. Queueing theory gives the shape. For one server with random arrivals, the mean time in the system, in multiples of the service time, is

W = 1 / (1 − ρ)

where ρ is utilisation. At 50% load a request takes twice its service time; at 90%, ten times. More servers sharing one queue keep that curve flat for longer, then turn the corner more sharply.This is the M/M/c model, computed with the Erlang C formula. Real service times are rarely exponential, but the knee is always there.

Read Fig 4 as a capacity rule: size a pool so that its busiest hour stays left of the knee. Past it, a small rise in traffic is a large rise in latency, and a hedge or a retry makes it worse.

What to measure

  • Per hop, the p50 and the p99, not the mean. The mean hides the tail that fan-out amplifies.
  • Utilisation of every pool, against the knee in Fig 4.
  • Timeouts per hop, set from that hop's p99.9, so a stalled dependency fails fast instead of late.
